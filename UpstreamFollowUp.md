- Перед раннім читанням профілю Booted-пристрою виконується `bootstatus` для його UUID і device set, з timeout 600 секунд та підтримкою cancellation. Додатковий `boot` не викликається.
- Регресійний fixture спочатку відтворив `Launchd unavailable` на старій реалізації для незмінного та зміненого профілю. Додано перевірки порядку команд, відсутності зайвих мутацій, device set та передачі timeout, cancellation і помилки читання користувачу.
- Після виправлення Xcode повідомив 46 успішних результатів звичайних тестів; збірка `SwiftSimSlim / My Mac`, Swift format lint та `git diff --check` пройшли. Live-runtime і візуальні перевірки не виконувалися.

## P2: дочекатися готовності launchd перед ранньою перевіркою профілю

- Файл: `SwiftSimSlim/Simulator/Backend.swift`, рядки 248–250, `ensure(_:desired:)`.
- Сценарій: симулятор ще завантажується, але `simctl list` уже повертає `Booted`. Користувач запускає Slim або Restore.
- Проблема: `disabled(device, log: true)` викликається без очікування `bootstatus`; помилка читання припиняє всю операцію.
- Наслідок: операція може завершитися помилкою замість очікування готовності пристрою. Це статично виявлений ризик, не відтворений тут на реальному runtime.
- Орієнтир upstream: https://github.com/MobAI-App/simslim/commit/4764434857dc1c2f2d99937f1414c5ca2ee3327b

### Запропоноване виправлення

1. Спочатку додати регресійний тест із підставним виконавцем команд: пристрій Booted, читання launchd не працює до успішного bootstatus. Тест має падати на поточній реалізації.
2. Перед раннім читанням для Booted-пристрою дочекатися готовності через bootstatus з наявним timeout і підтримкою cancellation. Простий варіант: використати `bootAndWait`; якщо потрібно зберегти мінімальну затримку для готового пристрою, розглянути раннє читання з одним повтором після очікування готовності. Не повторювати довільні помилки нескінченно.
3. Не вимикати і не перезапускати пристрій, якщо після очікування профіль уже збігається.
4. Зберегти перевірку allowlist, unmanaged overrides, device set, резервування пристрою, fallback та preserveBootState.

### Критерії приймання

- Booted, але ще не готовий: очікування готовності й успішна перевірка профілю.
- Профіль збігається: жодних shutdown, записів overrides або launchctl enable/disable.
- Профіль відрізняється: після готовності використовується наявний offline merge і перевірка результату.
- Timeout, cancellation і повторна помилка читання повертаються користувачу; жодного хибного успіху чи подальших мутацій.
- Залишається правильний device set у командах.
- Збірка схеми SwiftSimSlim для My Mac і релевантні звичайні тести проходять. Live-перевірку виконувати окремо лише за окремим запитом; її відсутність не видавати за runtime-доказ.

## Що не є виправленням нашої апки

- Затриманий прогрес у Go `applyDelta` (upstream `simctl.go:447–478`) стосується PR #51. Наш ServiceBatch читає завершення поступово через task group; переносити цю архітектуру з Go не потрібно.
- Swift CLI технічно можливий через окремий executable target і спільний backend. Повна заміна upstream також потребує реалізації CLI-контракту, doctor, top, watch, пакування та тестів. Це окрема можливість для автора, не погоджений обсяг робіт для нашої апки.
- Ліміт двох важких операцій і восьми service-команд обмежує паралельність роботи утиліти, а не RAM/CPU симуляторів. Жорстких квот ресурсів цей план не додає.
